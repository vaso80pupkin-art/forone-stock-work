# Как это проверено

Два набора автотестов и учебный сервер. Node.js установлен, внешних зависимостей нет.

```bash
cd tests
node gs-tests.js     # 117 проверок серверной логики Apps Script
node sync-tests.js   # 109 проверок клиентской очереди и слияния остатков
node mock-webapp.js 8099   # учебный Web App на реальном коде .gs
```

## gs-harness.js — эмулятор Google Apps Script

`vm`-контекст с мини-реализацией `SpreadsheetApp`, `LockService`, `PropertiesService`,
`Utilities` и объекта события для `doGet` / `doPost`. Благодаря этому `FORONE_Sync_v2.gs`
в тестах исполняется своим настоящим кодом, а не пересказом: проверка ключа, блокировка,
двухфазная запись, журнал, отклонения и дубликаты работают как в Google.

Покрытие `gs-tests.js`: ping и stock, ключ и список пользователей, битый JSON, HTML-ответ,
слишком большой пакет, отсутствие ID, невалижные тип/количество, не найденный артикул,
недостаточный остаток, резерв, дубли одного артикула и переименования, повтор после
отклонения, идемпотентность внутри пакета и между пакетами, пересчёт источника, конфликт
источника и журнала, блокировка параллельных записей, `FORONE_setup()` и `FORONE_selfTest()`.

## sync-tests.js — телефон без телефона

Модуль `sync-queue.js` загружается в `vm` с подставными `fetch`, `localStorage` и
состоянием приложения. Сценарии: генерация идентификаторов (20 000 за секунду уникальны),
миграция старой базы без полей синхронизации, очередь и сводка, statuses, офлайн без
единственного запроса, обрыв посередине отправки, пауза автоматического повтора и ручная
отправка поверх неё, отклонение складом без автоповтора, отмена с возвратом остатка,
обратная операция, досылка операций «сделанных до включения синхронизации», слияние
серверных остатков с дублями артикула, защита позиции с неотправленной операцией,
  BUSY-ответ, ошибки ключа, не-JSON ответы.

## mock-webapp.js — сквозная проверка

Поднимает настоящий `FORONE_Sync_v2.gs` на `http://localhost:<порт>/exec` с тестовыми
листами, плюс служебные ручки для проверки устойчивости:

| Адрес | Что делает |
| --- | --- |
| `GET /__chaos?fail=N&mode=html` | Следующие N запросов отдают HTML вместо JSON — типичное «забыли /exec» |
| `GET /__chaos?fail=N&mode=login` | Страница «нужно войти в проект» — публикация без доступа «Все» |
| `GET /__chaos?fail=N&mode=e500` | HTTP 500 |
| `GET /__chaos?fail=N&mode=busy` | HTTP 503 с кодом `BUSY` |
| `GET /__chaos?fail=N&mode=timeout` | Соединение висит без ответа (проверка 20-секундного таймаута) |
| `GET /__chaos?lock=1` | Блокировка Apps Script занята |
| `GET /__chaos?setSource=SKU=N` | Меняет остаток в листе-источнике |
| `GET /__chaos?sync=1` | Запускает `syncForoneStock` (пересчёт рабочего листа) |
| `GET /__stock` `/__journal` `/__errors` | Дампы листов для сверки с телефоном |
| `GET /__reset` | Сбоя нет, таблицы возвращены к исходному состоянию |

Так проверялось, что приложение: находит нужную позицию при повторяющемся артикуле, не теряет
операцию при обрыве, показывает причину отклонения, повторяет по команде человека и
сходится с сервером по всем остаткам после финальной сверки.

## Что стоит проверить руками перед релизом

1. Publish Web App, ввести URL и ключ, «Проверить соединение» → версия 2.0.0.
2. Одна позиция: расход → в `FORONE_Операции` появилась строка «Обработано», в
   `FORONE_Остатки` изменился остаток, на телефоне чип «Синхронизировано».
3. Выключить интернет на 30 секунд, включить → пилюля сначала показывает счёт, потом гаснет.
4. Расход больше складского остатка → «Отклонено» с текстом причины; довезли товар →
   «↻ Отправить снова» → «Синхронизировано», в журнале две строки одного ID.
5. Два телефона одновременно отправляют операции на одну позицию — остаток не «съедает»
   одну из операций (блокировка + `retry`).
