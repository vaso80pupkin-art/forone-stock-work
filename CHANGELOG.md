# Изменения

## 2.1.0 — синхронизация офисного источника и рабочей копии

* Офисная таблица и рабочая копия разделены. Офисный ID хранится в приватном Script Property `FORONE_SOURCE_SPREADSHEET_ID`; ID target фиксируется `FORONE_setup()` из связанной таблицы. ID новых частных файлов не хранится в публичном коде.
* `FORONE_setup()` сначала проверяет source ID и доступ к источнику, затем привязывает target к открытой копии. Старые защищённые книги допускаются только как read-only source, но всегда отклоняются как write target.
* Сервер выбирает вкладку по текущему месяцу и году. 17.11.2026 используется `Октябрь-Ноябрь`; после появления вкладки `Ноябрь-Декабрь` в декабре выбирается она; для января 2027 поддерживается `Декабрь-Январь 2027`.
* `GET stock` и операции синхронизируют актуальные данные источника в копию перед выдачей/обработкой. Триггер Apps Script повторяет сверку примерно каждые 15 минут; исходная офисная таблица остаётся только для чтения.
* PWA запрашивает остатки при запуске, возвращении на экран и восстановлении сети, затем примерно каждые 15 минут. После серверного merge каталог перерисовывается; офлайн-очередь операций сохраняется.
* Обновлён Service Worker до `forone-stock-work-v25`, чтобы телефоны получили новый клиентский код.
* Регрессии: 142 серверные и 113 клиентских проверки (255 всего), включая source/target изоляцию, разрешение защищённого ID только как read-only source, запуск Web App без активной книги и переход ноября 2026 → декабря → января 2027.

## 2.0 — двусторонняя синхронизация с Google Таблицей

### Новое в приложении

* Модуль `sync-queue.js`: локальная очередь операций, отправка пакетами, автоматические
  повторы с нарастающей паузой (10 с → 30 с → 2 мин → 10 мин → 30 мин), heartbeat,
  отправка при возвращении интернета и при возврате приложения на передний план.
* Запись операций в `FORONE_Операции` и чтение рабочих остатков из `FORONE_Остатки`:
  таблица становится источником истины по складу, исходный лист месяца не меняется.
* Блок «Отправка операций в Google Sheets (запись)» в карточке `ⓘ`: URL, ключ, имя
  сотрудника, метка устройства, три тумблера, «Проверить соединение», «Отправить сейчас»,
  «Сверить остатки», «Поставить в очередь», сводка (в очереди / с ошибкой / последняя
  отправка / последняя ошибка / версия Web App / время сверки).
* Жёлтая пилюля «N к отправке» в шапке, баннер в отчётах, статус и причина ошибки в каждой
  строке журнала, кнопки «↻ Повторить», «✕ Отменить», «↻ Отправить снова», «Убрать»,
  «↩ Вернуть товар» (обратная операция).
* Очередь и настройки синхронизации попадают в резервную копию JSON — база переносится на
  другой телефон вместе с незакрытыми операциями.
* `sw.js`: код приложения теперь отдаётся по схеме «сначала сеть, кэш как запас», поэтому
  после обновления телефоны не остаются на старой логике. Тяжёлые библиотеки и иконки
  остаются из кэша, офлайн-режим сохранён.

### Новое на сервере (`FORONE_Sync_v2.gs`, версия 2.0.0)

* `doPost` с действием `operations`: блокировка LockService, проверка ключа и пользователя,
  пакет до 100 операций, лимит количества, идемпотентность по `operationId`.
* `doGet` с действиями `ping` и `stock` — версия сервера, состояние листов, рабочие остатки.
* Двухфазная запись: сначала строка журнала со статусом «Принято», затем применение остатка
  и перевод в «Обработано». Сбой между фазами виден и разбирается.
* Лист `FORONE_Ошибки` для служебных сбоев, колонка «Расхождение» в рабочем листе,
  `FORONE_setup()` для создания листов и `FORONE_selfTest()` для самопроверки.
* Отклонённые операции записываются в журнал со статусом «Отклонено» и текстом причины —
  аудируемый след полный, остаток при этом не меняется.

### Исправления по результатам сквозного тестирования

Все семь пунктов найдены прогоном реального приложения против учебного Web App, а не
чтением кода:

1. **Дубли артикула.** Сопоставление позиции по одному артикулу списывало не ту строку
   (`H234-YP` в базе FORONE — и лувер, и панель). Сопоставление переведено на тройку
   «артикул + название + категория» и на три прохода слияния; позиции с неотправленной
   операцией защищаются от перезаписи.
2. **Одинаковые id новых позиций.** При добавлении серверной строки id строился только из
   артикула, и вторая позиция с тем же артикулом получала такой же id — выбор позиции в
   интерфейсе возвращал первую попавшуюся. id теперь уникальные.
3. **Отклонённая операция не могла быть повторена.** Отклонённые ID попадали в тот же набор,
   что и применённые, и повтор после «довезли товар» молча терялся как дубликат. Теперь
   применённые и отклонённые ID учатся раздельно: повтор с теми же данными принимается и
   помечается `retriedAfterRejection`, повтор с другими данными остаётся дубликатом.
4. **Досылка трогала отклонённое.** Кнопка «Поставить в очередь» брала операции со любым
   не-`synced` статусом и заново отправляла отклонённые и отменённые. Теперь только
   «Локально».
5. **Журнал не обновлялся после сбоя отправки.** Операция оставалась с чипом «Локально»,
   хотя в очереди уже была ошибка; приложение теперь извещается и о неудачной отправке.
6. **Пилюля и счётчики не считали сетевые ошибки** (только «в очереди» и «отклонено»),
   поэтому зависшую операцию было не видно. Добавлен `pendingTotal`, статусная строка
   «Ошибки отправки · N операций в очереди».
7. **Кнопки «Отправить сейчас» и «↻ Повторить» молчали во время паузы автоматического
   повтора**: выбор операции учитывал `nextTryAt` даже по прямой команде человека.
   Ручные команды теперь обходят паузу, автоматические — соблюдают.
8. **Устойчивость идентификатора.** Счётчик в `operationId` оборачивался каждые 1000 значений
   и при плотном потоке мог столкнуться; счётчик сбрасывается каждую секунду и дополняется
   случайным хвостом.

## 1.x — базовое приложение

Сканер и ручная проверка наличия, каталог с фильтрами, приход / расход / списание на замер,
резерв, отчёты за смену, импорт и экспорт XLSX, одностороннее чтение из Google Таблицы,
PWA-оболочка, тёмная и светлая темы.
