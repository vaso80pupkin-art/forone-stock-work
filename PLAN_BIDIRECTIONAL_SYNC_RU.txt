Сейчас приложение работает по безопасной односторонней схеме:

text
Исходные листы Google Таблицы
        ↓ чтение
FORONE_Остатки
        ↓ экспорт XLSX
FORONE Stock
        ↓
Локальная база телефона


Приложение может:

• загружать товары из Google Таблиц;
• обновлять локальный каталог;
• выполнять приход, расход и списание;
• учитывать резервы;
• сохранять операции локально;
• делать резервную копию.

Но приложение пока не отправляет изменения обратно в Google Таблицы:

text
FORONE Stock ──X──> Google Таблица


Даже если пользователю дать права редактора, обратная синхронизация сама не появится. Для неё нужно добавить отдельный канал передачи операций через Apps Script.

Целевая схема

Рекомендуемая архитектура:

text
Пользователь
    ↓
FORONE Stock
    ↓ POST-запрос
Apps Script Web App
    ↓ выполняется от имени владельца
FORONE_Операции
    ↓ обработка
FORONE_Остатки
    ↓
FORONE Stock


Основные исходные листы при этом остаются защищёнными и не изменяются напрямую.

Что будет реализовано

text

2. Web App в Apps Script

В существующий Apps Script добавляется обработчик:

javascript
doPost(e)


Он будет:

1. принимать JSON от приложения;
2. проверять обязательные поля;
3. проверять уникальный ID операции;
4. находить товар по артикулу;
5. проверять доступный остаток;
6. записывать операцию в FORONE_Операции;
7. обновлять FORONE_Остатки;
8. возвращать приложению результат.

Ответы будут иметь понятный формат:

json
{
  "ok": true,
  "operationId": "op-20261117-001",
  "message": "Операция записана"
}


При ошибке:

json
{
  "ok": false,
  "operationId": "op-20261117-001",
  "message": "Недостаточно доступного остатка"
}


3. Защита от повторной отправки

Это обязательная часть.

Если интернет прервётся после записи операции, приложение может повторить запрос. Чтобы расход не записался дважды, Apps Script будет проверять Operation ID.

Правило:

text
Одна операция с одним ID может быть записана только один раз.


Это защитит от двойного списания при:

• повторном нажатии;
• плохом интернете;
• перезагрузке страницы;
• автоматической повторной отправке;
• работе нескольких телефонов.

4. Очередь операций в приложении

В приложении появится локальная очередь:

text
pendingOperations


После операции:

• при наличии интернета она отправляется сразу;
• при отсутствии интернета сохраняется локально;
• после восстановления связи отправляется автоматически;
• пользователь видит количество неотправленных операций.

Статусы в интерфейсе:

text
Операция сохранена локально
Отправка…
Синхронизировано
Ожидает отправки
Ошибка отправки


Это важно, потому что склад может работать в помещении со слабой связью.

5. Настройки двусторонней синхронизации

В окне настроек появятся:

• URL Google Apps Script Web App;
• переключатель двусторонней синхронизации;
• кнопка «Проверить соединение»;
• статус подключения;
• количество операций в очереди;
• время последней успешной отправки;
• время последней ошибки.

Односторонний импорт из Google Таблиц останется отдельно:

text
Загрузить остатки из Google Таблицы


А отправка операций будет отображаться отдельно:

text
Отправка операций в Google Sheets


Важное решение по остаткам

Это главный архитектурный вопрос.

Нельзя просто каждый раз:

1. изменить остаток в приложении;
2. записать его в FORONE_Остатки;
3. через 15 минут снова полностью перезаписать FORONE_Остатки данными исходного листа.

Иначе ручной расход может исчезнуть.

Поэтому перед реализацией нужно закрепить правило:

Рекомендуемый вариант

Основные исходные листы считаются справочником и первоначальной базой товара.

FORONE_Остатки становится операционным складским листом, который изменяется через журнал операций.

Схема:

text
Исходные листы:
номенклатура, названия, категории, базовые данные

FORONE_Операции:
все движения товара

FORONE_Остатки:
актуальный рабочий остаток после операций


Apps Script будет:

• добавлять новые товары из исходных листов;
• обновлять названия и категории;
• сохранять рабочий остаток;
• применять новые операции;
• не затирать операционные изменения старым импортом;
• отдельно отмечать конфликты.

Конфликты

Если исходный лист и приложение изменили один и тот же остаток, система должна показывать:

text
Обнаружено расхождение по Н234-YP
Источник: 36
Операции: −4
Рабочий остаток: 32


Автоматически молча затирать такие данные нельзя.

Права доступа

Владельцу или аккаунту, под которым запускается Apps Script, нужны права Редактора на таблицу.

При публикации Web App выбирается:

text
Выполнять от имени: владелец скрипта
Доступ: пользователи по ссылке


Тогда сотруднику достаточно ссылки на приложение. Ему не обязательно выдавать права редактора Google Таблицы.

Но для безопасности желательно добавить хотя бы один из механизмов:

• секретный ключ Web App;
• разрешённый список пользователей;
• код организации;
• идентификатор сотрудника;
• ограничение по Google-аккаунтам Workspace.

Простой вариант «доступ всем по ссылке» удобен, но URL Web App фактически становится точкой записи. Поэтому в новой сессии отдельно проверим баланс удобства и безопасности.

Этапы реализации в новой сессии

Этап 1. Резервирование текущей версии

Перед началом:

• сохранить текущую версию Git;
• создать отдельную ветку или контрольный коммит;
• сохранить текущий sklad.zip;
• не ломать односторонний импорт;
• сделать резервную копию Apps Script.

Этап 2. Проектирование структуры таблицы

Создать и проверить:

text
FORONE_Операции
FORONE_Остатки
FORONE_Ошибки


Минимально обязательны первые два листа.

Этап 3. Реализация Apps Script

Добавить:

• doPost(e);
• проверку JSON;
• проверку артикула;
• проверку количества;
• проверку доступного остатка;
• идемпотентность по Operation ID;
• запись журнала;
• обновление рабочего остатка;
• JSON-ответ;
• журнал ошибок;
• функцию проверки связи doGet(e).

Этап 4. Публикация Web App

В Google Apps Script:

1. сохранить код;
2. запустить настройку;
3. подтвердить права;
4. создать развёртывание Web App;
5. получить URL;
6. проверить его тестовым запросом;
7. не передавать пароли или коды доступа в чат.

Этап 5. Доработка приложения

Добавить:

• URL Web App;
• очередь операций;
• отправку POST;
• автоматическую повторную отправку;
• статусы операций;
• счётчик ожидающих отправки;
• обработку ошибок;
• кнопку «Повторить отправку»;
• защиту от повторного нажатия;
• сохранение Operation ID.

Этап 6. Тестирование

Проверить по порядку:

1. тестовый приход;
2. тестовый расход;
3. тестовое списание;
4. недостаточный остаток;
5. повторную отправку той же операции;
6. отключение интернета;
7. восстановление интернета;
8. одновременную работу двух устройств;
9. отмену операции до отправки;
10. отмену операции после отправки;
11. обновление FORONE_Остатки;
12. появление записи в FORONE_Операции.

Этап 7. Ограниченный запуск

Сначала включить двустороннюю синхронизацию только для:

• одного пользователя;
• одной тестовой позиции;
• одной тестовой операции;
• одной копии таблицы.

После подтверждения результата подключать рабочую таблицу и остальных сотрудников.

Что понадобится от вас

В новой сессии понадобится:

1. подтверждение, что можно менять текущий Apps Script;
2. аккаунт с правами редактора таблицы;
3. возможность самостоятельно открыть Google Apps Script;
4. подтверждение разрешений Google;
5. URL опубликованного Web App;
6. тестовое разрешение на проведение одной операции.

Пароли, отпечатки пальцев и коды доступа передавать мне не нужно. Авторизацию выполняете самостоятельно в окне Google.

Что не будем делать

Мы не будем:

• менять исходные листы напрямую;
• хранить пароли Google в приложении;
• отправлять операции без уникального ID;
• молча затирать остатки;
• включать двустороннюю запись сразу для всех пользователей;
• удалять текущую одностороннюю синхронизацию до успешного теста.
